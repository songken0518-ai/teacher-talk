Python 核心 6 題
✓
Q6. Python 的 GIL 是什麼？對多執行緒有什麼影響？

GIL（Global Interpreter Lock）確保同一時間只有一個執行緒能執行 Python bytecode，所以多執行緒無法讓 CPU-bound 工作真正平行；I/O-bound 工作因為等待時會釋放 GIL，多執行緒仍能提升效率。CPU-bound 平行運算通常改用多行程（multiprocessing）繞過 GIL。

✓
Q7. list、tuple、set、dict 的差異與使用時機？

list 有序可變，適合順序資料；tuple 有序不可變，適合固定結構、可當 dict key；set 無序不重複，適合成員檢查與去重（O(1) 查找）；dict 是 key-value 對應，O(1) 查找，Python 3.7+ 保留插入順序。

✓
Q8. 什麼是 decorator？舉一個實際用途。

decorator 是接收函式、回傳（通常是包裝過的）函式的高階函式，用 @ 語法套用。常見用途：日誌記錄、計時、權限檢查、快取（functools.lru_cache）、FastAPI 的路由註冊（@app.get(...)）。

✓
Q9. Python 的記憶體管理／垃圾回收機制？

CPython 主要靠參考計數（reference counting），物件參考數歸零立即釋放；另外搭配分代垃圾回收（generational GC）處理循環參考的情況，單靠計數無法回收。

✓
Q10. 什麼時候該用 generator 而不是回傳 list？

處理大量或無限資料、或只需要迭代一次時用 generator（yield）,因為是惰性求值、不用一次把所有結果放進記憶體；需要隨機存取、多次迭代、或需要 len() 時才用 list。

✓
Q11. 型別提示（type hints）對大型專案的實際好處？

讓 IDE／mypy 靜態抓出型別錯誤、當作活文件、搭配 Pydantic 可以直接做執行期驗證；缺點是需要額外維護成本，且 Python 執行期預設不強制檢查。

非同步 / asyncio 5 題
✓
Q12. async/await 解決什麼問題？跟多執行緒差在哪？

async/await 是單執行緒內的協作式併發，用事件迴圈在等待 I/O 時切換去做別的工作，沒有執行緒切換與鎖的開銷，特別適合大量 I/O-bound（如呼叫外部 API）的場景；多執行緒是作業系統層級搶佔式排程，有 context switch 成本，且 Python 受 GIL 限制無法用多執行緒做真正平行的 CPU 運算。

✓
Q13. 呼叫 OpenAI API 時，為什麼要用非同步（AsyncOpenAI）而不是同步？

LLM API 呼叫通常要等好幾秒，同步呼叫會整個佔住一個 worker；非同步下，等待回應時可以釋放事件迴圈去處理其他請求，在高併發情境下吞吐量明顯更好。

✓
Q14. FastAPI 裡，什麼時候該寫 async def，什麼時候用一般 def？

端點內若呼叫的都是非同步函式庫（httpx.AsyncClient、AsyncOpenAI、非同步 DB driver）就用 async def；若必須呼叫阻塞的同步函式庫，用一般 def，FastAPI 會自動丟到 thread pool 執行，避免卡住事件迴圈。

✓
Q15. asyncio.gather 和依序 await 的差別？

依序 await 每個協程要等前一個完成才開始下一個，總時間是總和；asyncio.gather 同時發起多個協程，等待全部完成，總時間接近最慢的那一個——適合同時呼叫多個獨立 API。

✓
Q16. 忘記 await 一個 coroutine 會發生什麼事？

該協程不會真正執行，Python 通常會印出 RuntimeWarning: coroutine was never awaited；常見在測試或忘記加 await，導致邏輯「看起來跑了但其實沒有」，是很難 debug 的 silent bug。

FastAPI / API 設計 6 題
✓
Q17. FastAPI 怎麼用 Pydantic 做請求驗證？好處是什麼？

定義 BaseModel 描述請求／回應的欄位型別，FastAPI 會自動依 model 驗證傳入的 JSON，型別不對或缺必填欄位會自動回 422 並附上詳細錯誤訊息；好處是驗證邏輯集中、型別即文件，還能自動生成 OpenAPI schema／Swagger UI。

✓
Q18. FastAPI 的依賴注入（Depends）解決什麼問題？

把共用邏輯（DB session、驗證使用者身份、取得設定）抽成獨立函式，用 Depends() 注入到路由函式，路由函式不用重複寫這些邏輯；也方便測試時用 dependency override 換成假的實作。

✓
Q19. 怎麼設計 API 的錯誤處理？

用 HTTPException 搭配明確狀態碼（400 參數錯誤、401/403 權限、404 找不到、422 驗證失敗、500 伺服器錯誤），錯誤訊息結構化（error code + message），並用 exception handler 統一格式，不要讓例外裸露 stack trace 給前端。

✓
Q20. RESTful API 設計原則簡述？

用名詞複數表示資源（/users、/orders），用 HTTP method 表示動作（GET 查、POST 建、PUT/PATCH 改、DELETE 刪），狀態碼準確反映結果，分頁／篩選用 query string，版本控制（/v1/...）方便日後相容。

✓
Q21. 怎麼設計串流（streaming）回應的 API endpoint（例如 LLM 逐字輸出）？

FastAPI 用 StreamingResponse，搭配 async generator 逐段 yield 資料（例如 OpenAI 的 stream=True 逐 chunk 轉發），前端用 Server-Sent Events 或直接讀 chunked response 即時顯示；要注意連線中斷時正確關閉上游串流，避免資源洩漏。

✓
Q22. API 要怎麼做速率限制（rate limiting）？

常見做法是在 middleware 或 API gateway 層用 token bucket／sliding window 演算法，依 IP 或 API key 限制單位時間請求數，搭配 Redis 儲存計數以支援多台伺服器共用；超過限制回 429，並在 header 附上剩餘額度／重置時間。

OpenAI / LLM API 整合 8 題
✓
Q23. 什麼是 function calling / tool use？實際用途？

讓模型不直接生成最終答案，而是輸出「要呼叫哪個工具、帶什麼參數」的結構化 JSON，由程式執行真正的邏輯（查資料庫、呼叫外部 API）再把結果餵回模型；用途包括讓 LLM 存取即時資料、執行計算、操作系統，避免模型憑空捏造。

✓
Q24. 怎麼確保模型回傳的是合法 JSON、符合你要的 schema？

用 OpenAI 的 structured outputs／response_format（json_schema 模式）強制模型輸出符合指定 schema 的 JSON；程式端仍要用 Pydantic 再驗證一次，防止極端情況，驗證失敗時要有重試或降級機制。

✓
Q25. 怎麼控制 LLM API 的成本與延遲？

選對模型（小模型做簡單任務、大模型留給真的需要推理的步驟）、控制 max_tokens、用 prompt caching（重複系統提示詞可省 token）、必要時用 streaming 提升感受速度、能本地判斷的邏輯先擋掉不必要的呼叫。

✓
Q26. 呼叫 OpenAI API 失敗（timeout、rate limit、5xx）時，程式該怎麼處理？

用指數退避（exponential backoff）重試，區分可重試錯誤（429、5xx、timeout）與不可重試錯誤（400、401）；設定重試上限與逾時時間避免無限重試；重要路徑要有 fallback，而不是整個服務掛掉。

✓
Q27. 怎麼寫呼叫 LLM API 的程式碼的單元測試？

用假的／注入的 client（dependency injection 或 monkeypatch）取代真實 OpenAI client，讓測試不打真實網路、不花錢、結果穩定；但要另外保留至少一條真的打 API 的整合測試或手動驗證，因為 prompt 在真實模型上的行為無法只靠 mock 驗證。

✓
Q28. 什麼是 RAG（Retrieval-Augmented Generation）？基本流程？

讓模型回答前先從外部知識庫檢索相關內容，再把檢索到的內容放進 prompt 讓模型基於這些資料回答，減少幻覺、能用到訓練資料之外的即時資訊。流程：文件切塊 → embedding 向量化 → 存進向量資料庫 → 提問時做相似度搜尋取回相關片段 → 組合成 prompt 交給模型生成答案。

✓
Q29. embedding 是什麼？怎麼選擇 chunk size？

embedding 是把文字轉成高維向量，語意相近的文字在向量空間距離也相近，用於相似度搜尋；chunk size 太大會讓不相關內容混進去降低精準度，太小會失去上下文，通常抓幾百 token 並保留一些重疊，實際數值要依資料型態測試調整。

✓
Q30. 怎麼防止 prompt injection？

明確區分系統指令與使用者輸入，不要把不信任的內容直接串進系統 prompt；對工具呼叫結果做白名單／權限限制，模型建議的動作不代表可以無條件執行；高風險操作要有人工確認或額外驗證層。

Prompt 工程與安全 5 題
✓
Q31. 系統提示詞該怎麼設計，才不會讓模型「過度保守」不呼叫工具？

明確列出「什麼情況下應該呼叫哪個工具」，而不是只堆一堆否定式限制（不要做這個、不要做那個）；過多否定式指令會讓模型傾向不作為，要用真實 API 實測驗證行為，不能只憑直覺寫。

✓
Q32. few-shot prompting 是什麼？什麼時候該用？

在 prompt 裡放幾個「輸入-輸出」範例，幫助模型理解期望的格式與風格；適合輸出格式較特殊、zero-shot 效果不穩定的情境，缺點是會增加 token 成本。

✓
Q33. 怎麼讓模型的輸出更穩定、可重現？

降低 temperature（甚至設 0）、用 structured output 限制格式、明確給出格式範本與邊界條件，必要時對關鍵欄位再做規則式後處理驗證，不完全依賴模型「一次就對」。

✓
Q34. 使用者輸入裡可能藏惡意指令，想誘導模型洩漏 system prompt 或做不該做的事，怎麼防？

系統提示詞不放機密邏輯或金鑰、明確告知模型忽略使用者輸入中「試圖改變角色或規則」的內容、高風險輸出（執行程式碼、存取檔案）加額外的程式端權限檢查，不能只靠 prompt 層面的「請不要」。

✓
Q35. 怎麼評估／比較不同 prompt 或不同模型的效果？

建立一組具代表性的測試案例（含邊界情況），定義可量化的評分標準（格式正確率、關鍵資訊命中率、人工評分），跑 A/B 比較不同版本，避免只憑幾次主觀感覺判斷。

測試策略 5 題
✓
Q36. 單元測試、整合測試、端對端測試的差別？

單元測試針對單一函式／類別，隔離外部依賴，快、多；整合測試驗證多個元件一起運作（例如真的連 DB），較慢、較少；端對端測試模擬使用者真實操作整個系統流程，最慢、最少，但最貼近真實使用情境。

✓
Q37. mock 跟 fake 的差別？

mock 是用假物件記錄呼叫並可斷言被呼叫的方式與次數；fake 是有簡化但真實邏輯的替代實作（例如用記憶體字典模擬資料庫），行為更接近真實但仍不碰外部系統；兩者都用來讓測試不依賴真實外部服務。

✓
Q38. 為什麼「所有 mock 測試都綠燈」不代表程式真的沒問題？

mock 測試驗證的是「你的程式邏輯」對「你假設的外部行為」是否正確，但如果對外部服務（例如 LLM）的真實行為假設錯了，mock 測試完全測不出來；關鍵路徑仍需要至少一次真實呼叫驗證。

✓
Q39. 怎麼測試會呼叫外部 API 的程式碼，又不想每次都真的打 API？

用依賴注入把 client 抽象化，測試時注入假的 client 回傳預先寫好的回應；也可用錄製/重播（如 VCR）記錄一次真實回應後續重播；正式環境用真的 client。

✓
Q40. 測試覆蓋率越高代表程式越沒問題嗎？

不一定，覆蓋率只代表程式碼「有沒有被執行過」，不代表「有沒有斷言對的行為」；覆蓋率該當參考指標而非唯一目標。

系統設計與維運 6 題
✓
Q41. 設計一個「使用者上傳文件 → LLM 回答問題」的系統，你會怎麼切模組？

文件上傳/儲存層、文件解析與切塊層、embedding 與向量資料庫、檢索層、prompt 組裝與 LLM 呼叫層、回應快取層；模組間用清楚介面隔開，方便個別測試與替換。

✓
Q42. 怎麼做快取來降低 LLM API 成本與延遲？

對完全相同或高度相似的請求做結果快取（Redis，key 用輸入內容的 hash），搭配 prompt caching；要注意快取失效策略，避免回傳過期或不適用的答案。

✓
Q43. 系統要怎麼監控／觀測 LLM 呼叫的健康狀況？

記錄每次呼叫的延遲、token 用量、成功/失敗率、錯誤類型，設定異常告警；建議記錄部分輸入輸出（去識別化）方便事後追查品質問題，但要注意隱私與資料保留政策。

✓
Q44. 怎麼處理 API 金鑰與敏感設定？

絕對不寫死在程式碼或提交進版本控制，用環境變數／.env（加進 .gitignore）或雲端 secret manager；金鑰要能輪替，且依環境（開發/正式）分開管理。

✓
Q45. 如果 LLM API 突然大量逾時或整個掛掉，系統該怎麼降級？

設定合理 timeout 與重試上限避免請求堆積拖垮服務、對非核心功能提供降級回應、用 circuit breaker 在偵測到持續失敗時暫停呼叫一段時間，避免持續打向已經掛掉的服務。

✓
Q46. 怎麼設計 API 版本管理，讓舊客戶端不會突然壞掉？

用路徑（/v1/、/v2/）或 header 做版本區分，新版本上線後舊版本維持一段棄用過渡期並提前公告，避免破壞性變更直接覆蓋舊行為。

資料庫 / SQL 基礎 4 題
✓
Q47. 什麼時候該建索引（index）？索引的代價是什麼？

常用來 WHERE 篩選、JOIN、ORDER BY 的欄位適合建索引，能大幅加快查詢；代價是佔用額外儲存空間，且每次 INSERT/UPDATE/DELETE 都要同步維護索引，寫入效能會下降。

✓
Q48. SQL Injection 是什麼？怎麼防？

攻擊者把惡意 SQL 片段混進輸入參數，讓資料庫執行非預期指令；防法是一律用參數化查詢或 ORM，絕不用字串拼接組 SQL，並對輸入做基本驗證。

✓
Q49. ORM（如 SQLAlchemy）的優缺點？

優點是用物件操作資料庫、減少手寫 SQL、內建防注入、跨資料庫可攜性較好；缺點是複雜查詢效能可能不如手寫 SQL、抽象層可能隱藏低效查詢（例如 N+1 問題），需要懂底層 SQL 才能有效除錯。

✓
Q50. 什麼是 N+1 查詢問題？怎麼解決？

查一筆列表後，對列表中每一筆再各自發一次查詢取關聯資料，總查詢數是 1+N 次而非 1 次；解法是用 JOIN 或 ORM 的 eager loading（例如 SQLAlchemy 的 joinedload）一次把關聯資料抓齊。

情境題與收尾提問 5 題
✓
Q51. 面試官問「你遇過最困難的技術問題是什麼，怎麼解決的？」該怎麼回答？

用 STAR 結構（情境、任務、行動、結果）簡潔講一個真實案例，重點放在「怎麼分析問題、嘗試過什麼、最後怎麼驗證解法真的有效」，避免只講結果不講過程。

✓
Q52. 面試官問「你有什麼問題想問我們？」該問什麼？

問實質內容而非禮貌性提問：團隊目前的技術棧與這個職缺會碰到的實際任務、code review／部署流程、團隊怎麼評估一個人做得好不好、這個職缺半年內最優先要解決的問題是什麼。

✓
Q53. 被問到不會的技術問題，該怎麼回應？

誠實承認不熟，但展示思考路徑（「沒有直接用過，但猜可能跟…有關，如果是我會先查…／用…驗證」），不要瞎掰或裝懂，面試官通常更在意解決問題的方法而不是背答案。

✓
Q54. 被要求現場寫程式時，時間快來不及了，該怎麼辦？

先跟面試官說明目前進度與還差什麼，優先確保核心邏輯能跑、其餘用註解或口頭說明打算怎麼做；講清楚取捨與思路，通常比硬塞完整但有 bug 的功能更加分。

✓
Q55. 怎麼在最後幾分鐘給面試官一個好印象的總結？

簡短總結今天展示了什麼能力、對這個職缺的興趣點在哪、接下來打算怎麼準備／補強目前的不足，展現主動與自我覺察，而不是單純道謝。

對照 面試流程卡 與 面試模擬 一起用；答案只是方向，實際回答要結合你自己的專案經驗
